# LockNote v1.1.0 Release Notes

Release date: October 24, 2026

This release focuses on **data safety** and **robustness**. It fixes three issues that could cause data loss or permanently unrecoverable notes, and adds the core test coverage and CI checks that were previously missing.

## Data Safety

### Restore validates vault ownership
- Before restoring, LockNote decrypts notes from the backup to confirm they belong to the current vault.
- A backup from a different vault is rejected with a clear message pointing to recovery-key import, instead of silently overwriting existing notes.

### Restore is rollback-safe
- Affected files are snapshotted into `restore-snapshots/` before being replaced.
- A failure midway restores the snapshot automatically, so data is never left half-old and half-new.
- The note content cache is cleared after a successful restore.

### Master key can no longer be overwritten
- A failed vault-state read is no longer mistaken for a first run.
- Setup double-checks that no master password exists and refuses to overwrite an existing vault.
- Vault writes are split into `INSERT` (first setup) and `UPDATE` (password change / reset).

### No lost drafts
- Pending debounced edits are flushed before switching notes, locking the app, or closing the window.
- Window close now asks the frontend to save first and waits up to 3 seconds before quitting.

### Durable writes
- New `internal/fsutil` helper: `fsync` before `rename`, plus a directory `sync`, so a power loss cannot leave an empty or half-written file.
- Notes, history versions, attachments, and exports all use this path.

## Robustness

- **Readiness guard**: every API call goes through `coreOrErr()`, returning a clear error instead of panicking when the core is not ready.
- **Versioned migrations**: `PRAGMA user_version` is tracked; a failed migration blocks startup with a reason instead of silently degrading to an empty list.
- **SQLite tuning**: WAL journal mode and `busy_timeout=5000`.
- **Note content cache**: list and search reuse decrypted content; the cache is cleared on lock.
- **ZIP limits**: 500 MB per file, 4 GB total, 100,000 entries, on top of the existing path-traversal guard.
- **Image attachment limit**: 50 MB per image, with the data URL length checked before decoding.
- **Startup failure handling**: startup retries are capped at 120 attempts and surface the actual error instead of looping forever.

## UI and Localization

- Startup progress, table-of-contents toggles, and backup safety hints are now part of i18n across Simplified Chinese, Traditional Chinese, and English.
- Removed remaining hardcoded Chinese strings from the sidebar and editor.
- The backup screen now explains what a backup contains and when restore is allowed.

## Engineering and Tests

- New CI workflow running `go vet`, `go test`, `tsc --noEmit`, and `npm test`; the Go version follows `go.mod`.
- Duplicate release workflows merged into a single multi-platform build with macOS signing and notarization.
- New `npm test` script runs the full frontend suite.
- Core test coverage changes:

## Compatibility

- Data format is fully compatible with 1.0.x. No migration is required; existing notes, todos, images, settings, and backups are preserved.
- Behavior change: **restoring a backup from a different vault is now rejected**. This is the fix, not a regression. To move to a new device or a different vault, use recovery-key import.
- Backup contents are unchanged from 1.0.9 (notes, history, attachments only). The new `restore-snapshots/` directory is never included in a backup.

## Known Limitations

- Tag names, notebook names, original attachment filenames, and smart-view filters are still stored in plaintext in the local database. See the "Security Model" section of the README.
- Recovery-key validation still accepts 5–32 arbitrary characters. Use the 16-character key generated by the app.
